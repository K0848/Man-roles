# Agent Note: Knip 的装配用途与导出边界

Status: implemented

## 问题

人物产品的两个插件由 Cordis YAML 加载，部分开发依赖是公开装配 peer 的同版本镜像。仅从 TypeScript import 判断会误报这些声明；正式文档中的 SDK 手动入口和 Windows 系统工具也需要登记。另一部分报告来自只在本文件使用、却额外对外导出的实现，二者需要分别处理。

## 决策

[静态扫描清单](../../../../config/analysis/knip.json)保留原有工作区范围，[动态配置入口](../../../../config/analysis/knip.ts)通过[装配适配器](../../../../scripts/knip-cordis.ts)读取公开源码中的 Bundle manifest、Loader YAML、静态 profile 模板及已组合 Web 层的浏览器值导入。配置分析不启动产品、不执行 Loader 表达式，也不读取用户数据或依赖已构建 lib。

只有存在实际装配用途的运行依赖，以及同名同版本的 peer/dev 镜像声明，才获得对应 workspace 内的精确说明。用途消失或新增没有装配证据的依赖时，Knip 仍应报告；不使用包名前缀全局忽略。已有生产依赖和公开 peer 契约保持，额外裁剪作为独立兼容性变更评估。

SDK 构建脚本按已有文档登记为手动工具入口，PowerShell 登记为 Windows 系统工具。没有匹配文件的测试 glob 按当前目录动态展开；未来测试出现时自动恢复扫描，不把 src 全部改成入口，也不放宽未使用导出的检查。

九个仅在同文件消费的导出收为内部声明，保留函数、schema 和类型实现。`ResearchEvidenceKind` 仍供公开证据字段与实际 Cordis 类型目录使用，保留导出并用单项 `@public` 描述其公开用途。六个 package 公开入口的声明须在重建后与修改前保持一致。

## 备选方案

- 按报告直接删除模块、依赖或函数：会混淆静态识别缺口与实际无用途内容。
- 全局忽略 workspace 依赖或文件内部使用的全部导出：会隐藏未来真正冗余的声明。
- 手工维护九个长期豁免包名：容易在 YAML 或 profile 改动后失去依据，改由现行公开装配元数据推导。
- 为零报告而收缩现有 peer 契约：把静态维护变成公开兼容性变更，不属于本次最小修改。

## 后果

检查按真实用途工作，原扫描范围与生产装配保持。配置适配限定一个声明式 Bundle 的元数据边界；不支持的 profile 静态形式应显式报错，不猜测或执行源代码。公共用途标记需要明确消费者，不能作为未核实导出的通用消警方式。

## 验证

[配置回归](../../../../scripts/knip-cordis.spec.ts)验证实际动态依赖、失去用途、新增无用声明和未来测试文件。Knip 完整运行须零报告；相关产品回归、Host/Client 类型、六个公开入口声明、完整 Cordis 类型目录及文档检查共同覆盖导出变更。
